Abstract
KA V ACH is a web application for monitoring authentication activity, detecting rule-based lo-
gin anomalies, and supporting security investigation through an AI tool interface. The im-
plementation separates a React frontend from a Java 21 Spring Boot backend and uses Post-
greSQL through Spring Data JPA. Authentication uses BCrypt password veriﬁcation and bearer
JSON Web Tokens; administrative operations and selected user-speciﬁc resources are protected
through role and ownership checks.
The detection pipeline evaluates six conditions: failed login, unusual login time, login in-
volving an inactive account, a previously unseen IP address, a previously unseen device string,
and repeated failures within a ten-minute window. Each anomaly has a ﬁxed severity and
weight. User risk is calculated from anomaly weights recorded during the preceding 24 hours
and capped at 100. Dashboard services combine login statistics, severity totals, recent critical
anomalies, and a ranked user watchlist.
The AI component includes structured anomaly explanations and a two-loop orchestration
service. An inner loop performs bounded model/planner and tool cycles; an outer loop pro-
cesses supplied follow-up requests. Thirteen registered tools expose investigative queries and
selected account or telemetry operations. A deterministic fallback supports operation when live
inference is unavailable. This report documents the implementation, diagrams its data ﬂow,
explains detection rules, and presents a reproducible validation plan. It distinguishes source-
conﬁrmed behavior from proposed improvements and makes no measured accuracy, through-
put, or production-readiness claims.
Keywords: authentication telemetry, anomaly detection, risk scoring, Spring Security, two-
loop agent, security dashboard.

CHAPTER 1
Introduction
1.1 Project Overview
Authentication records are useful evidence for investigating account misuse. A record can show
whether an attempt succeeded, which account was involved, when the attempt occurred, and
the associated network and client information. Individually, these events can be difﬁcult to
interpret. Grouping them with account state and recent history provides a more useful basis for
investigation.
KA V ACH combines login telemetry, deterministic anomaly detection, risk summaries, audit
records, and an AI-assisted investigation interface in one web application. Its name refers to a
shield. The project is implemented as a Spring Boot REST backend and a React single-page
frontend. PostgreSQL stores the application entities. Implementation descriptions in this report
refer to the supplied source snapshot [ 1].
The application supports ADMIN and USER roles. Administrators can inspect
organization-wide information and manage accounts through designated endpoints. Or-
dinary users can access selected views of their own activity. AI agent roles describe
investigative and operational behavior; these are distinct from the authenticated user’s security
role.

Chapter 1. Introduction
1.2 Problem Statement
A basic login implementation can reject incorrect credentials without providing enough context
for later investigation. A log viewer may display records without explaining their relationship
to account risk. KA V ACH addresses the problem of connecting authentication events to under-
standable alerts, recent account risk, and an investigation workﬂow within a small, inspectable
application.
The project asks how a login event can be evaluated using explicit rules, how alerts can
be summarized into a bounded user score, and how a conversational tool interface can retrieve
relevant application information. The current work implements these capabilities while leaving
statistical validation and deployment hardening as further work.
1.3 Objectives
1. Implement registration and authentication with encoded passwords and bearer tokens.
2. Persist login activity and evaluate six explicit detection rules.
3. Present anomalies, risk, trends, account status, and audit events through role-aware pages.
4. Support structured AI explanations with a deterministic fallback.
5. Implement bounded tool calling and continuation through supplied follow-ups.
6. Document the architecture and the tests needed to establish correctness and security.

Figure 1.1 summarizes implementation boundaries. The browser communicates with the back-
end rather than directly with PostgreSQL or the model provider. Services coordinate persis-
tence, rule evaluation, and AI interactions.

1.5 Scope and Boundaries
The project is an application-level monitoring prototype. Its rule engine does not train a
machine-learning model. IP addresses are compared with stored history; no external reputation
lookup is implemented. The device rule compares supplied strings, including user-agent
information on the authentication path; it is not a cryptographically veriﬁed device identity.
An inactive-user alert concerns the account active ﬂag, not elapsed account dormancy. Quar-
antine refers to setting an account inactive, affecting later authentication and JWT checks. It
does not imply operating-system isolation or ﬁrewall enforcement.
No production trafﬁc dataset, benchmark run, or labelled evaluation corpus was supplied.
Quantitative performance and detection-accuracy claims are excluded. Interface workﬂows in
Chapter 5 are source-derived descriptions rather than captured runtime screenshots.
1.6 Organization of the Report
Chapter 2 presents requirements and dependencies. Chapter 3 explains data ﬂow, persistence,
and access boundaries. Chapter 4 details authentication, detection, risk, and AI operation.
Chapter 5 describes interfaces and validation scenarios. Chapter 6 concludes with limitations
and future work. Appendices map ﬁndings to source and explain report compilation.

2.2 Functional Requirements
2.2.1 Authentication and Accounts
Registration shall validate data, reject duplicate usernames and email addresses, encode pass-
words, and create active ordinary-user accounts by default. Login shall check account existence,
active state, and password validity. Successful login shall return a token and safe account de-
tails. Failed and blocked requests shall produce appropriate errors and audit events.

Chapter 2. Requirement Analysis
2.2.3 Risk and Analytics
Risk shall aggregate weights of anomalies detected in the last 24 hours, cap the score at 100, and
map it to four named levels. Organization-wide views shall include severity totals, risky-account
totals, login outcomes, a seven-day trend, and a ranked watchlist of at most ten accounts.
2.2.4 AI and Tool Operations
The system shall provide anomaly explanations, user analysis, security summaries, history,
chat, and agent-loop execution. The agent response shall include steps and tool outputs for the
browser. Deterministic planning or advisory fallback shall support demonstrations when live
inference is unavailable.
Tools shall expose names, argument schemas, role assignments, and parallel-safety meta-
data. Because some tools change accounts or create telemetry, authorization requirements must
apply to the execution boundary as well as the visible page.
2.3 Non-Functional Requirements
These are requirements and implementation observations, not benchmark results. A database
audit table does not establish tamper resistance, and bearer authentication does not prove every
object-level access check is correct.
2.4 Execution Environment and Assumptions
Development requires Java 21, a Node.js environment compatible with the frontend dependen-
cies, and PostgreSQL. Live inference requires provider conﬁguration and network access. Cre-
dentials should be supplied through the existing conﬁguration mechanisms; none are included
in this report.
No measured minimum hardware speciﬁcation is available. Hardware and concurrency re-
quirements must be established by testing rather than assigning unsupported RAM or CPU

Design Analysis
3.1 Layered Design
Controllers receive HTTP requests, apply declared access restrictions, and pass inputs to ser-
vices. Services implement authentication, telemetry, detection, scoring, analysis, and orchestra-
tion. Repository interfaces express persistence operations and aggregate queries. DTOs shape
responses so clients receive page data without directly controlling entity persistence.
The frontend organizes features as pages and shared layout/UI components. Authentica-
tion and theme contexts hold browser state. A common Axios client adds bearer credentials,
normalizes failures, and emits diagnostic information. These boundaries make the workﬂows
traceable to source modules [ 1].

3.14 Database Constraints and Time Semantics
Username and email columns are unique. Login-event indexes cover user ID, time, status, and
IP address. Anomaly detection timestamps differ from login timestamps: risk uses detection
time, while brute-force counting uses login time. Inserting historical events therefore requires
careful interpretation.
The anomaly existence check uses user ID, rule type, and login-event ID. It prevents re-
peated sequential insertion but does not establish a database-level uniqueness guarantee under
concurrency. Analysis history stores summaries, explanations, indicators, recommendations,
conﬁdence, model, advisory status, and cached identiﬁers. The audit entity provides persis-
tence, without a demonstrated append-only or cryptographic integrity mechanism.

4.1 Registration and Authentication
Registration trims the username, normalizes email, rejects duplicates, encodes the password,
and creates an active USER account. It records an audit event and returns safe account ﬁelds.
Login uses BCrypt password matching, which is hashing rather than reversible encryption.
Unknown usernames generate an audit event and an unauthorized response without user-
linked telemetry. A known inactive account is blocked and failed telemetry is attempted. Incor-
rect passwords for active users also produce failed telemetry. V alid credentials produce a JWT,
success audit entry, and successful login record.
JWT is a claims representation deﬁned in RFC 7519 [ 2]. The browser sends the token with
later requests; the backend validates it and rechecks current account state. Browser logout clears
local authentication information and should not be described as server-side token revocation.
4.2 Telemetry Recording
Authentication recording uses a REQUIRES_NEW transaction annotation, intended to preserve
telemetry independently of a failing authentication transaction. It supplies defaults for missing
IP , device, and location, saves the event, and invokes detection. The caller catches recording
exceptions, so a telemetry failure can occur without replacing the main login response.

can reﬂect legitimate movement or network changes. The interface should support comparing
related events and account context rather than implying that every rule match is an attack.

CHAPTER 6
Conclusion and Future Work
6.1 Conclusion
KA V ACH integrates authentication telemetry, six deterministic rules, recent user risk, dash-
board summaries, audit records, and a tool-assisted AI workﬂow. Frontend pages, API con-
trollers, services, repositories, and entities make the processing stages traceable.
The detector provides explicit reasons and ﬁxed weights. The risk service summarizes re-
cent evidence in a bounded score. Structured explanations and the two-loop interface add an
investigation mechanism with deterministic fallback. Together, these components support a
practical application-level security-monitoring demonstration.
The evidence supports implementation conclusions, not production-readiness claims, de-
tection accuracy, or measured latency improvements. This report identiﬁes the tests required to
assess those properties instead of assigning unsupported ﬁgures.
6.2 Current Limitations
The ﬁxed off-hours rule does not learn personal schedules. IP/device baselines use strings, can
include failures, and do not establish hardware identity or geographic plausibility. Weights lack
empirical calibration, and multiple alerts from a single event can saturate risk quickly.

Chapter 6. Conclusion and Future Work
The brute-force query has no explicit event-time upper bound. Time conventions and his-
torical input need careful handling. Some queries read full history, and duplicate prevention
requires concurrency validation. Agent tools combine queries and state changes, making consis-
tent authorization essential. Steering is request-local, execution is sequential, and the frontend
timeout may be shorter than a multi-cycle agent request.
6.3 Future Direction of Work
6.3.1 Centralized Tool Policy
Check authenticated principal, action, resource ownership, and arguments before every tool in-
vocation. Introduce review or approval for consequential changes where appropriate. Record
the initiating principal, target, outcome, and rationale instead of relying only on generated nar-
rative.
6.3.2 Detection and Data Quality
Adopt a consistent time-zone-aware timestamp convention, enforce intended event windows,
and test out-of-order input. Consider successful-login baselines and bounded history for IP/de-
vice rules. Calibrate thresholds using representative labelled data and publish false positives as
well as detections.
6.3.3 Audit Integrity and Reliability
Add appropriate uniqueness constraints, transaction tests, and telemetry-failure monitoring. De-
ﬁne retention and access controls. If stronger integrity is needed, evaluate append-only storage,
external export, or tamper-evident veriﬁcation instead of assuming database persistence supplies
it.
6.3.4 Agent Sessions and Interaction
Introduce authenticated job/session identiﬁers and a channel for progress, steering, and can-
cellation. Bound outer-loop work and request size; make operational tools idempotent where
