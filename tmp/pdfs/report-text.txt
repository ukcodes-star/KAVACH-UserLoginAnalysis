Abstract
KA V ACH monitors login activity and applies explicit rules to identify unusual events. It pro-
vides an AI tool interface for investigating those events. A React frontend communicates with
a Java 21 Spring Boot backend, which stores data in PostgreSQL through Spring Data JPA.
BCrypt veriﬁes passwords, and bearer JSON Web Tokens authenticate later requests. Role and
ownership checks protect administrative operations and selected account resources.
The detector checks six conditions: a failed login, a login at an unusual hour, an inactive
account, an unseen IP address, an unseen device string, and repeated failures within a ten-minute
window. Each matching rule assigns a ﬁxed severity and weight. The user risk score sums
anomaly weights from the preceding 24 hours and caps the result at 100. The dashboard presents
login statistics, severity totals, recent critical anomalies, and a ranked account watchlist.
The AI service produces structured anomaly explanations and runs a two-loop workﬂow.
The inner loop executes bounded model or planner cycles and application tools; the outer loop
processes follow-ups supplied with the request. Thirteen registered tools provide investigative
queries and selected account or telemetry operations. A deterministic fallback handles requests
when live inference is unavailable. This report describes the implementation, data ﬂows, detec-
tion rules, and a reproducible validation plan. Accuracy, throughput, and production readiness
have not been measured; proposed improvements are identiﬁed separately from implemented
behavior.
Keywords: authentication telemetry, anomaly detection, risk scoring, Spring Security, two-
loop agent, security dashboard.

CHAPTER 1
Introduction
1.1 Project Overview
Login records help investigators examine account misuse. Each record identiﬁes an account,
an outcome, a time, and network or client details. A single event provides limited context.
Comparing it with account state and earlier activity can explain why it deserves attention.
KA V ACH brings login records, rule-based alerts, account risk, audit history, and AI-assisted
investigation into one web application. Its name means a shield. The application has a Spring
Boot REST backend, a React frontend, and PostgreSQL storage. The implementation described
here is the supplied source snapshot [ 1].
ADMIN and USER are the application security roles. Administrators can inspect activity
across accounts and manage users through designated endpoints. Ordinary users have selected
views of their own activity. The AI investigator and operator roles describe agent behavior; they
do not replace the signed-in user’s permissions.
1.2 Problem Statement
Rejecting an incorrect password leaves an investigator to determine which account was targeted,
whether failures repeated, and whether the client was familiar. KA V ACH connects login records

with alerts and recent account risk to support that investigation in a small application with
inspectable logic.
The project evaluates login events with explicit rules, combines the resulting alerts into a
bounded account score, and lets a conversational interface retrieve relevant application data
through tools. Statistical validation and deployment hardening remain further work.
1.3 Objectives
1. Implement registration and authentication with encoded passwords and bearer tokens.
2. Persist login activity and evaluate six explicit detection rules.
3. Present anomalies, risk, trends, account status, and audit events through role-aware pages.
4. Support structured AI explanations with a deterministic fallback.
5. Implement bounded tool calling and continuation through supplied follow-ups.
6. Document the architecture and the tests needed to establish correctness and security.
1.4 System Block Diagram
Figure 1.1 shows the browser, API, service layer, and external dependencies. Browser requests
go through the backend, which controls access to PostgreSQL and the model provider. Appli-
cation services save records, evaluate rules, and coordinate AI requests.
1.5 Scope and Boundaries
KA V ACH is a prototype for monitoring activity within the application. Detection uses ﬁxed
rules without training a machine-learning model. The IP rule compares stored addresses and
performs no external reputation lookup. The device rule compares supplied strings, including
user-agent information captured during authentication; those strings do not verify a physical
device.

2.2 Functional Requirements
1. V alidate registration, reject duplicate usernames/emails, hash passwords, authenticate ac-
tive accounts, and return JWTs with safe user details.
2. Record known-account login outcomes and permit administrator-created demonstration
events with account, timestamp, status, IP , device, and location ﬁelds.
3. Evaluate six independent rules, preserve each triggered anomaly, and check the user/-
type/event combination before inserting a duplicate.
4. Aggregate recent anomalies into a capped 24-hour risk score and expose severity totals,
login outcomes, a seven-day trend, and a ten-account watchlist.
5. Provide role-aware account, telemetry, anomaly, audit, and AI views; apply ownership
checks to selected personal resources.
6. Support advisory explanations, analysis history, bounded tool calling, and deterministic
fallback when live inference is unavailable.
2.3 Quality and Operating Requirements
Protected requests must authenticate the caller and enforce role or ownership checks at sensi-
tive entry points. Tool execution needs the same action-level policy. Alerts must preserve the
matching rule, its reason, and its ﬁxed weight. Controllers, services, repositories, DTOs, and
pages divide these responsibilities across the application.
Reliability testing must check failed-login transactions, repeated detection, and recording
failures. Performance testing must cover history queries, pagination, and AI requests with sev-
eral execution cycles. UI screenshots provide no measure of load capacity or detection accuracy.
Report examples omit local conﬁguration values. Timestamp rules use LocalDateTime,
so deployment needs a consistent time convention. Demonstration events must be identiﬁable
alongside real login evidence. The project has no established minimum hardware speciﬁcation
or calibrated attack probabilities.

Design Analysis
3.1 Layered Design and Access Boundaries
HTTP controllers validate inputs and pass work to services. Services apply business rules and
use JPA repositories to read entities and calculate aggregates. DTOs deﬁne the API data con-
tracts. React pages share authentication and theme state and send requests through an Axios
client [1].
Authentication routes are public; other requests pass through the security chain. The JWT
ﬁlter validates the token, looks up the current account, rejects inactive users, and sets the ac-
count role. Method security and selected ownership checks then restrict access to resources [ 3].
Registry tools enter services through a separate path, which needs equivalent authorization.
The client sends JSON with bearer credentials and uses a 30-second timeout. Unauthorized
responses clear stored session state. Agent execution can span several model and tool cycles,
so its timeout, cancellation, and retry behavior need coordination with the client. Appendix C
lists the direct endpoint scopes.

3.7 UML Sequence: Two-Loop Investigation

CHAPTER 4
Functioning of the System
4.1 Registration and Authentication
Registration trims the username, normalizes email, checks duplicates, and encodes the pass-
word. It creates an active USER account, saves an audit event, and returns safe ﬁelds. Login
checks passwords with BCrypt, a one-way hashing scheme.
An unknown username produces an audit failure and an unauthorized response, with no
user-linked login record. A known inactive account is blocked, and the service attempts to
record a failed login. It also records failed telemetry for an active account with an incorrect
password. V alid credentials produce a JWT, a success audit entry, and successful login teleme-
try.
JWT represents claims in the format deﬁned by RFC 7519 [ 2]. The browser attaches the
token to later requests. The backend validates it and rechecks the current account state. Browser
logout clears local authentication data; it does not revoke the token on the server.
4.2 Telemetry Recording
The recording method has a REQUIRES_NEW annotation to preserve telemetry independently
of a failed authentication transaction. It supplies missing IP , device, and location values, saves

The inactive-account rule reads a Boolean ﬂag; it does not calculate dormancy from the last

For a failed event at te, the repository counts failures with tlogin > t e − 10 minutes. The query

to prevent duplicates during sequential reanalysis. Concurrent requests could both pass this
check. A unique constraint or locking policy needs veriﬁcation under concurrent execution.

4.6 Two-Loop AI Orchestration
An agent request contains a prompt and may include context, a role, steering messages, and
follow-ups. The service creates a local conversation, execution-step lists, and queues populated
from the request. The outer loop starts an inner invocation and then processes the supplied
follow-ups.
At the start of each inner iteration, the service adds at most one queued steering message
to the conversation. The model or fallback planner returns text and any tool calls. The service
resolves each tool by name, executes it, and adds its result or error to the conversation for the
next cycle. The inner loop can ﬁnish when no tool calls or steering remain, and each invocation
has a six-iteration limit.
Each follow-up starts another inner invocation. The ﬁnal response contains text, execution
steps, tool names, loop counts, mode, model, and completion time. Investigator and operator
specializations affect behavior within one service and conversation; they do not run as separate
agents.
Steering and follow-ups are ﬁxed when the request begins. This execution path has no
channel for messages typed while it is running, so live steering requires further work. Tools run
sequentially, including those whose metadata declares parallel safety.

CHAPTER 6
Conclusion and Future Work
6.1 Conclusion
KA V ACH records authenticated login activity, applies six explicit detection rules, and calculates
a capped 24-hour account risk score. Security views and audit records support investigation.
The LLM interface connects requests to thirteen application tools through a two-loop service,
with deterministic fallback when live inference is unavailable. The repository and screenshots
show the implementation and interface design. Detection accuracy and production performance
still require measurement.
Limitations. Fixed login hours and comparisons of IP or device strings can identify unusual
values without establishing account compromise. The weights remain uncalibrated. The brute-
force query has no explicit upper time bound, and duplicate prevention needs concurrency test-
ing. Steering is local to each request, tools run sequentially, and operational tools need consis-
tent authorization. Storing audit records alone provides no demonstrated tamper resistance.
Future work. The next priorities are a centralized authorization policy for tools, reliable event-
time handling, database constraints, and integration tests for each rule. Agent sessions need au-
thentication, cancellation, and live steering. Audit retention needs protection, and query limits
and concurrent performance need testing. A labelled evaluation corpus should guide threshold
calibration before adding learned anomaly models, external SIEM integration, or more authen-
tication factors.
